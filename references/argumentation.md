# 論証と構成の規範

[k16shikano / japanese-tech-writing](https://gist.github.com/k16shikano/fd287c3133457c4fd8f5601d34aa817d) を統合した、技術文書の論証・構成・視点の規範。

表現の規範（[phrases.md](phrases.md) / [structures.md](structures.md)）が「どの語・どの型を消すか」を扱うのに対し、本ファイルは「論理にツッコミどころを残さないか」を扱う。記事・X 投稿のような短文では前者が中心になり、技術書の章・解説文では本ファイルの規範が効く。

スコアリングでは測れない。pass/fail で点検する。

## 論証の厳密さ

文章の論理にツッコミどころを残さない。書き上げたら、読み手の反論を先回りして次を点検する。

### 推量を機械的に断定化しない

「かもしれない」「だろう」「ようだ」「らしい」は、根拠なく主張を弱めている場合だけ削る。

事実未確認の可能性、作中人物の認識、ログからの推定、読者が抱きそうな疑念、反実仮想を表す場合は、その不確実性を保つ。断定に直せるのは、本文内の根拠によって命題が確定している場合に限る。

| 種別 | 扱い |
|:---|:---|
| 根拠なく弱めているだけ | 断定に直す（または根拠を足す） |
| 事実未確認の可能性 | 不確実性を残す |
| 作中人物・エージェントの認識 | 不確実性を残す |
| ログ・観測からの推定 | 不確実性を残す |
| 読者が抱きそうな疑念 | 疑念のまま書く |
| 反実仮想（もし〜なら） | 仮定のまま書く |

**Before**:
> AI は的外れな提案を提示し続けている。

（本文には「提示し続けている」を確定させる根拠がない）

**After**:
> AI は的外れな提案を提示し続けている可能性がある。

**変更点**: 推定を断定に変えず、不確実性を保ったまま文を整える。逆に、本文内の根拠で確定しているなら「提示し続けている」と言い切ってよい。

### 別物を「同じ」とまとめない

区別すべき対象（別々の決定、別々の原因、種類の違う問題）を一括りの言葉でくくらない。

**Before**:
> チームは同じ決定を別々に下していた。

**After**:
> どれも別々の決定であり、しかも互いに依存している。

**変更点**: 相互依存する別々の未決事項を「同じ」とまとめず、腑分けする。

### 単一原因に還元しない

複数の要因がある事象を、一つの原因に押し込めない。例が複数種類の問題を含むなら、それぞれを切り分け、どの道具がどれを説明するのか対応づける。

**Before**:
> この事故は情報隠蔽の問題だ。

（実際には契約の不在と情報隠蔽の失敗が混ざっている）

**After**:
> この事故には二つの原因がある。一つは工程間の契約が定義されていなかったこと、もう一つはエラーが上流に共有されなかったことだ。前者は契約設計で、後者は可観測性で防ぐ。

**変更点**: 混在した原因を切り分け、それぞれにどの対策が効くか対応づける。

### 因果は機構を示す

「A だと B になる」とだけ書いて理由を省略しない。なぜそうなるのかを一文添える。

**Before**:
> 手順で分けると変更が全体に波及する。

**After**:
> 各工程がデータを受け渡すための表現を共有してしまい、その表現を変えると全体に波及する。

**変更点**: 「波及する」の機構（共有された表現が変わる）を一文で示す。

### 「必ず」と書かない

検出・保証・解決を無条件にできるかのように書かない。条件付きで正確に述べる。

| 過剰 | 修正 |
|:---|:---|
| 「必ず検出できる」 | 「〜のときに検出しやすい」 |
| 「すべて解決する」 | 「〜できることが多い」 |
| 「保証される」 | 「〜が成り立つときに限り保証される」 |

何かを否定・限定するときは、否定する命題そのものを「」で正確に書き出す。「明文化されていればすべてを任せられる」を意味しない、のように。「何もかもが解決するわけではない」のような漠然とした否定で済ませない。

### 概念の扱いを全体で揃える

章・節をまたいで、同じ概念の分類・定義・用語の地位を一致させる。

ある節で「人間が決める」と分類したものを、別の節で「チームで合意する」と書かない。節の中心となる語は、その節以前に定義・対象範囲を述べてから使う。複数の概念を一つの上位語にまとめるときは、命名の直前に、それらが同じものに帰着すると一文で述べる。

### 例が主張を支えるか確認

挙げた例が主張の全体を支えているかを確認する。例が主張の一部しか支えないなら、主張の範囲を例に合わせて狭める。

「次節で扱う」と前方に逃がした論点は、本当にそこで回収されることを確認する。回収しない伏線を張らない。譲歩や限定（「ただし」「とはいえ」）を置いたら、その後で必ず論を進める。逆接で終えて宙吊りにしない。

## 段落と論証の構成（パラグラフライティング）

段落は論証の一歩であり、読者は段落単位で論理を追えなければならない。

- 一つの段落には一つのトピックだけを置く。場面の進行（調査、報告、検証、評価）が複数混ざった長い段落は、一歩ずつの段落に分割する。
- 段落の最初の文を読めば、その段落が何の話かわかるようにする。
- 段落の先頭では、前の段落との論理関係を接続表現で明示する（「であれば」「実際」「しかし」「この例自体からも」）。
- 論証は一方向に進める。結論を出してから反論を処理し、結論を言い直す構成にしない。反論と疑念の処理を終えてから、結論を一度だけ置く。
- 読者が立てそうな誤った解釈は、明示的に否定してから本当の理由を述べる（「その理由は『〜だから』ではない。〜だからだ」）。
- 山場で効かせたい情報（数値、固有の事実）は、その手前の段落で先出ししない。
- 「後の章で扱う」のような前方参照は、論証が一段落した位置（段落末・節末）に置く。論証の途中に挟んで流れを切らない。

### 「A ではなく B」の扱い（本家ルールとの調停）

本家 stop-slop は二項対立（「X ではなく Y」）を telegraphed reversal として全面禁止し、Y を直接述べよと定める（[structures.md](structures.md) 参照）。

技術文書の論証では、読者の誤った解釈を否定してから正す形が必要になる場面がある。その場合は **否定の根拠を一文添える**ことを条件に許容する。反実仮想（「もし A なら、〜だっただろう」）が使えることが多い。

| 形 | 判定 |
|:---|:---|
| 「X ではなく Y だ」（根拠なし、ドラマ演出） | 禁止。Y を直接述べる |
| 「その理由は X ではない。〜だから Y だ」（否定の根拠あり） | 許容 |
| 「もし X なら〜だったはずだが、実際は Y だ」（反実仮想） | 許容 |

## 読み手の負荷の管理

読者の記憶と注意は有限の資源として扱う。

- 後で参照する必要のない固有名（ファイル名、関数名、識別子）を出さない。「仕様書」「金額計算のユーティリティ」のような一般的な言い方で済ませる。
- 例の節の中でも、その節の問い・帰結に関係しない過剰な詳細だけを omit する。議論に必要な具体は残す。省略の典型は、エージェント報告の装飾的精度（時刻、HTTP ステータス、カバレッジ率など）や、後で参照しない固有名。
- 抽象的な言い回しの指す内容が文脈から一意に決まらないときは、丸括弧による同格挿入でその場で特定し、読者に前を読み返させない。
- 新しい例や場面を追加して読者が保持すべき文脈が増えるときは、前の例と何が違うのか、なぜもう一つ必要なのかを前置きする。

### 本家ルール（具体性）との切り分け

本家 stop-slop は曖昧な断定を具体的な数字・固有名に置換せよと定める（[examples.md](examples.md) 例 8・例 20）。本ファイルは後で参照しない固有名を落とせと定める。矛盾ではない。

| 場面 | 判定 |
|:---|:---|
| 主張の山場で効く数値・固有の事実 | **出す**（曖昧さを消す） |
| 後で参照しない固有名・装飾的精度 | **落とす**（記憶負荷を減らす） |

**Before**:
> エージェントは 14:32:07 に `validate_invoice()` を呼び、HTTP 200 を受け取り、カバレッジ 87.3% を報告した。請求書の検証は通った。

**After**:
> エージェントは請求書の検証ユーティリティを呼び、検証が通ったことを報告した。

**変更点**: 後で参照しない時刻・関数名・ステータス・カバレッジ率（装飾的精度）を落とす。一方、金額や件数のように主張の山場で効く数値なら残す。

## 視点と語り

- 例示では、結果の羅列や受動態（「特定され、判明した」）ではなく、行為者を主語にした動作の連なり（「リポジトリを調査して特定し、見つけてくれた」）で書く。
- 「入社2年目のエンジニアが」のような架空の人物設定を無意味に冠しない。
- 論証の中で読者を「あなた」と呼ばず、役割名（「開発者」「読者」）で書く。二人称の呼びかけは、場面への導入（「〜としよう」）や章・本の結びなど、限られた要所にとどめる。
- 章や節で術語（K、契約、不変条件など）を導入したら、以後はその語で通す。「文脈」「ツール」「AI」のような曖昧語に後退しない（定式化する前の導入語として使うのはよい）。
- 対象を指す語は具体的に選ぶ。「AI」「ツール」のような広い語でぼかさない。
- 術語・訳語は、その分野で慣用されている語を選ぶ（プッシュ通知は「配送」ではなく「配信」、など）。意味の近い漢語を一般語の感覚で充てない。
- 人物そのものに言及するときは原綴りで書く（Lehman、Bainbridge）。歴史上の人物や、人名を冠した概念を定着名で紹介するときは、日本語で通用しているカタカナの通称を使う。
- 術語の響きを持つ語を、術語でない場面に流用しない（システムから人間までの連なりを「経路」と呼ぶ、など）。「届くまでの流れ」のように普通の言い方で書く。

### register による「あなた」の調停

| 文章の種別 | 二人称の扱い |
|:---|:---|
| 技術書の章・解説文（論証中心） | 役割名で書く。「あなた」は要所のみ |
| 記事・ブログ（説明中心） | 場面導入では「あなたが〜する場面では」を使ってよい |
| X 投稿・口語の短文 | 「あなた」を使ってよい（本家 False Agency 修正どおり） |

本家 stop-slop は False Agency の修正で「特定の人がいない場合は『あなた』で読者を主語にする」を勧める（[structures.md](structures.md)）。技術文書ではこれより役割名を優先する。読者を場面に置きたいときは、二人称ではなく具体的な行為者を名指しする方法を先に試す。

## 見出しの付け方

見出しは内容を特定できる具体的なものにする。その節が答える問い、または扱う対象を指す句にする。

- 作業の手順だけを述べる見出し（「例に戻す」「〜を読み直す」）や、情報量のない見出しにしない。
- 見出しを、節の結論を言い切る「セリフ」にしない。見出しの時点で読者がオチを知る状態を避ける。
- 節で扱っている対象を指す名詞句でもよい。
- 疑問形か断定形かは問わない。問うのは、扱う対象や読者の持つ問いを指しているかである。本文のトーンに合うほうを選ぶ。

| 種別 | 例 | 判定 |
|:---|:---|:---|
| 手順だけ | 「例に戻す」「設定を読み直す」 | 不可。扱う対象を見出しにする |
| 結論のセリフ | 「テストこそが institutional memory だ」 | 不可。オチを先に出している |
| 扱う対象を指す名詞句 | 「ループ不変条件と帰納法」 | 可 |
| 答える問い | 「カバレッジは何 % あれば足りるか」 | 可 |

## 読者への誠実さ

- 例が作為的に見えうる場合、それを隠さない。読者の疑念を先回りして認め、現実に十分あり得ることの根拠を短く添える。
- その根拠は、著者の断定（「十分あり得る状況だ」）ではなく、読者自身の経験に訴える一般的事実や通説に求める（「この症状は珍しくないだろう」「〜という言い方もよく耳にする」）。
- 確認していないことを、確認したかのように滑らかに書かない。

**Before**:
> この例では請求書が三重に届く。これは十分あり得る状況だ。

**After**:
> この例では請求書が三重に届く。再送とリトライが重なるこの種の重複は、運用していれば珍しくないだろう。

**変更点**: 「十分あり得る」という著者の断定を、読者の経験に訴える一般的事実（再送とリトライの重複）に置き換える。
